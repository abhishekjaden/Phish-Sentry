1. Who operates PhishSentry

Abhishek Jaden Vethanayagam operates PhishSentry. For privacy or support requests, contact abhishekjaden@gmail.com.

PhishSentry helps users examine selected phishing indicators in web addresses, credential-form structure and explicitly selected email, understand findings and choose related protection actions. Results have limited coverage: no configured warning is not proof that a page or message is safe. Service availability does not establish independent model accuracy or production qualification.

2. What Connected handles, and when

Account registration and sign-in

Connected service features use a PhishSentry account. Users do not need their own AWS account. The extension's registration form sends the username, email address and account password directly to Amazon Cognito over HTTPS. Confirmation and recovery involve the username and verification code or new password as requested by the account service. Password and verification-code fields in the registration form are cleared after requests and when leaving the form; they are not saved in the observation feed.

Cognito provides verification, hosted sign-in and password recovery. Sign-in uses an authorization-code flow with PKCE. The extension holds access and refresh credentials in Chrome session storage restricted to trusted extension contexts. Signing out clears those extension credentials and session findings and attempts token revocation and identity-provider session cleanup. A cleanup failure can be reported. An existing access token can remain usable until it expires, and a browser sign-in session with the identity provider may remain. Sign-out is not account deletion.

Visited pages and requested hostname checks

Automatic or requested hostname checks can send the hostname to the PhishSentry service. Routine hostname requests omit the URL path, query and fragment. Some configured domains bypass the automatic hostname-service call; that does not establish safety or disable applicable page checks.

Packaged scripts inspect selected top-document page structure and credential-form indicators locally. They do not read typed website-password values or capture screenshots. Frames, shadow-root forms and script-driven behavior can limit coverage. The separate account password needed for registration or sign-in is handled as described above.

Browser protection starts off on a fresh installation; a saved preference can be retained. When enabled, selected detected warnings can pause access in the affected tab. Page requests or scripts can run before a warning appears. Protection decisions, review choices and approvals can be included in the browser observation.

Selected email analysis

Email analysis is requested explicitly by the user, with the displayed disclosure and consent step. Selected details from a supported open Gmail message, or details manually supplied in the workbench, can include the sender, reply-to information, subject, visible message text, links, attachment names and supported capture evidence. Those details go to the PhishSentry analysis service. This flow does not silently scan the entire inbox or upload attachment file contents.

The application processes the submitted details to return analysis. It does not intentionally save raw email-analysis inputs as cloud findings. This application behavior is separate from operational network and provider processing described below. Avoid submitting passwords, verification codes or unnecessary confidential information. Messages can contain sensitive personal information even though PhishSentry does not seek it for a separate health, financial or advertising purpose.

Security-coach questions

A question submitted to the security coach goes to the PhishSentry service, including when the answer is fixed reference guidance. Do not paste passwords, access keys or confidential content into a question.

Optional cloud summaries

Live cloud sync starts off. You can explicitly send one observation's redacted summary or consent to syncing future observations. Enabling sync does not automatically upload all older findings.

Summary payloads contain the observation type, warning level, selected indicator codes and protection action, where applicable. They exclude hostnames, email text, sender details, questions, passwords and account tokens. A session credential separately authorizes the request, and accepted records are associated with the signed-in account. The summary service also records identifiers and timestamps needed for delivery and receipt handling. Redaction does not make the request anonymous.

AWS acceptance and receipt readback are separate outcomes shown by the workbench. Pausing sync, clearing local observations, signing out or uninstalling does not erase records already accepted by the service.

Optional AI and public-site inspection

Generated AI guidance and public-site inspection are disabled in the current reported service configuration. Their appearance in the interface does not mean that they are available. If offered later, their provider, processing details and choices will be disclosed before use.

The optional AI flow, if enabled and explicitly chosen for a question, sends that question, selected indicator codes and reference context through Amazon Bedrock. It does not automatically attach an email body or account token to the prompt; text that you paste into the question is included. The optional site-inspection flow, if enabled and separately consented to, sends a public hostname and path, excluding query and fragment, for a bounded static-HTML fetch. The destination website receives the service's request. That inspection does not execute the site's scripts.

Read aloud and downloaded observations

Read aloud plays fixed recordings bundled with the extension. The recordings were prepared using gTTS and Google Translate from fixed translated explanation sentences, not users' emails or browsing observations. Playback stays on the device, uses no microphone and does not send your selected message or finding to a runtime speech service.

You can download a selected observation. That creates a file on your device; it does not upload the observation. You control that file, which remains after signing out or clearing the feed.

3. Where data is stored and for how long

DataHandling
Browser observationsUp to 200 observations are held for up to 30 minutes in the extension's browser-worker memory. They clear on sign-out, account change or worker restart. Page observations can contain hostnames. Raw email text, sender/subject details and credentials are excluded from this feed.
Hostname result cacheConnected can cache up to 300 hostname/result entries for up to 30 minutes in the browser worker. These hosted results are not written to the persistent local-mode cache, and the active cache clears when the signed-in session changes.
Preferences and protectionPreferences and relevant protection state are stored by the extension. Up to 200 paused-tab records can retain the target URL and warning evidence in restricted Chrome session storage. These targets stay inside the extension. They can survive a worker restart, and sign-out does not silently release a warning. This protection state is separate from the observation feed.
Account recordsCognito keeps account records separately from the extension session. Signing out or uninstalling does not delete them. The Connected release does not provide automatic expiry for inactive or unconfirmed accounts or an in-product account-deletion button. Use the support process below for account requests.
Authentication credentialsThe public Connected client is configured for 15-minute access and ID tokens and 30-day refresh tokens, with revocation enabled. These token lifetimes are not account-record retention periods or a guarantee of immediate rejection after sign-out.
Accepted cloud summariesThe findings service stores account-associated redacted summaries in an encrypted DynamoDB table. The application assigns a 24-hour logical expiry and excludes expired records from its reads. DynamoDB TTL is enabled, but physical cleanup is asynchronous: expiry does not mean deletion happens at exactly 24 hours.
Operational logs and network metadataHTTPS services receive connection metadata, including IP addresses. The observed API access, Lambda and EKS control-plane log groups are configured for seven-day retention. EKS API, audit and authenticator logging is enabled; application load-balancer access and connection logs to S3 are disabled. These settings do not establish one retention period for every provider-managed security record, container collector or other infrastructure log.
Backups and copiesPoint-in-time recovery is disabled for the current findings table. No completed backups, AWS Backup recovery points or exports were reported in the inspected resource-scoped Mumbai listings on 28 October 2026. This is not a promise that all provider-managed copies or archives cease to exist when an application record expires.
DownloadsDownloaded observation files stay on your device until you delete them. Clearing the browser feed does not remove these files.

The above deployment settings were checked on 28 October 2026. PhishSentry does not use device GPS or request a geolocation permission. Ordinary IP and connection-metadata handling still occurs. The service may also keep bounded in-memory state to limit abuse; that state is separate from storing raw email contents.

4. Your choices and privacy requests

You can leave browser protection and live cloud sync off, decline optional uploads, clear session findings, sign out or remove the extension. A selected email or question is sent when you choose its analysis action. These controls have different effects: clearing local data does not delete your account or accepted cloud records.

Send access, correction, account-closure or cloud-record deletion requests to abhishekjaden@gmail.com. Requests are handled through support, rather than an automatic in-product deletion control. The operator may need to verify that a request relates to your account before taking account-specific action. Do not send passwords, verification codes or access tokens.

No immediate or fixed-deadline erasure guarantee is made. An account or cloud record should not be assumed deleted merely because a request was sent, sign-out succeeded, or a local count returned to zero. Support can explain the action taken and any records that remain subject to operational, security or legal retention.

5. Providers, purposes and sharing

PhishSentry uses Amazon Web Services for hosted analysis, account identity and optional account-linked cloud records. The reviewed application, identity and findings deployment is in Mumbai, India. This does not mean that every email-delivery component, provider support system, log or backup is processed exclusively in India.

This privacy page is hosted on GitHub Pages, whose host receives ordinary web-request metadata when you open it. Domain registration and DNS infrastructure use Cloudflare. The currently supplied DNS configuration uses DNS-only records for the public application, rather than Cloudflare's HTTP proxy. Loading the privacy page or resolving the domain is separate from choosing to send email details for analysis. These providers should not be confused with a claim that no third parties are involved.

Data is used for the disclosed phishing-indicator checks, related explanations, protection choices, account access and optional summary delivery, and for necessary operation and security of those features. PhishSentry does not sell user data, use it for advertising or unrelated profiling, or use it for creditworthiness or lending. Submitted emails and questions are not used to train PhishSentry models.

Transfers are limited to the services described here and permitted operational, security or legal purposes. Human access is limited to specifically consented support, necessary security or legal purposes, or permitted aggregated and anonymized internal operations.

PhishSentry's use and transfer of user data complies with the Chrome Web Store User Data Policy, including its Limited Use requirements.

6. Extension permissions

  • tabs: associate navigation, selected-page checks and findings with the correct browser tab.
  • storage: keep preferences, protection state and restricted authentication-session storage.
  • notifications: show warnings associated with phishing indicators.
  • alarms: schedule expiry, rechecks and cleanup of temporary protection state.
  • declarativeNetRequest: apply scoped session navigation rules supporting user-enabled browser protection.
  • identity: complete hosted authentication redirects.
  • HTTP/HTTPS host access: run packaged page checks and warnings, capture supported selected-email details after explicit action and consent, and communicate with the configured service and identity endpoints. This is not permission to silently scan the entire inbox.
